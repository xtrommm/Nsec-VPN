# Device VIP recovery and native splash

Base reviewed: main `4e80875` (merged PR #12). Existing UUID installation identity and device-held registration proof are in KeyStoreManager.kt:60–74; auth.ts:24–40 rejects ID-only ownership changes. VIP, promo redemptions and purchase ownership already live in PostgreSQL. Clearing cache does not erase that identity; clearing storage does. Android does not provide a secure app-private credential that can be relied upon to survive Clear Storage.

## Implemented behavior

- Original Settings Device ID is the recovery identifier. It is not a secret and cannot grant access alone.
- Settings → Device VIP Recovery → Protect VIP sets an 8–12 digit private PIN over HTTPS. Save the original Device ID and PIN separately before clearing app data. PINs are not persisted on the phone or returned in APIs. Only a salted bcrypt hash (cost 12) and recovery-failure/lock metadata are stored on the backend. Obvious weak PINs are rejected. Changing an existing PIN requires its current PIN.
- After clearing storage, Settings → Device VIP Recovery → Restore VIP accepts the ORIGINAL ID and PIN, authenticates that same backend record, replaces device registration proof and returns the existing tier/expiry. Promo redemption, purchase ownership and server requests remain on the same record. Expired VIP stays expired. This is secure manual restoration, not an automatic hardware-ID lookup. No new grant or duplicate promo redemption is generated by restoration.
- Recovery increments the device auth epoch and revokes refresh tokens; authentication rejects stale access-token epochs. Both registration and refresh issuance bind tokens to epochs, closing a stale-registration/refresh race. Old legacy tokens default to epoch zero and keep working until that device recovers. Active peer leases are expired for cleanup, retaining addresses until agent removal; cleanup normally occurs on its existing next tick, and unreachable nodes retain reservations until removal/agent expiry. A new connection replaces that node's previous peer safely.
- Missing, unconfigured or blocked identities never return credentials. Five incorrect PIN attempts persist a 15-minute lock in the DB. Existing global/auth rate limits remain. No client-IP, raw PIN, private-key, token or browsing logging is added. API administrative device selectors do not expose recovery hashes.
- Device ID shown in Settings updates to the recovered original ID immediately. Recovery is rejected while a local tunnel is connected/connecting/disconnecting; disconnect first. The recovery UI has busy/validation/failure/status retry states. Wrong PIN failures are not retried as authentication failures. Expired normal app sessions can refresh before authenticated recovery-settings calls.
- If storage was already cleared BEFORE a PIN was configured, knowing Device ID alone is insufficient. The old entitlement record still exists, but recovery requires operator-assisted ownership verification. Do not turn public Device ID into a bearer credential or allow unverified paid-token transfers.

## Splash and first-connect

The screenshot was the original Android launch window, not the extra Compose page. That extra page, its 250ms delay and its obsolete UI tests are removed. Android 12+ uses `android:windowSplashScreenBrandingImage`; the vector is 200×80dp with a real twelve-star EU flag and `Made in Europe` lettering. Pre-12 uses a launch-window layer list. Day/night resources provide contrast; native launch resources follow Android's system light/dark configuration. The existing full logo asset replaces the white-on-white monochrome launch graphic. Android's exact launch-window rendering requires phone verification.

`Accept & Continue` is now `Continue`. Prominent disclosure/affirmative action and Android's `VpnService.prepare()` permission remain. They are not bypassed or silently accepted; first-install or clear-data users may still see them. ## API and migration

Additive endpoints:
- GET `/api/v1/auth/recovery/status`: authenticated; `{success,data:{configured}}`, never a hash.
- PUT `/api/v1/auth/recovery/pin`: authenticated; `{pin,currentPin?}`; currentPin required to replace a configured PIN.
- POST `/api/v1/auth/recover-device`: `{deviceId,pin,registrationSecret}`; new credential is 64 lowercase hex digits. Returns the existing register-device response shape with credentials for the same record. Never paste the request PIN/secret or response tokens into chat.

Error codes: INVALID_RECOVERY_PROOF (401), RECOVERY_LOCKED (429), DEVICE_BLOCKED (403), RECOVERY_UNAVAILABLE (500), existing validation/rate-limit errors, and TOKEN_REVOKED (401) on stale session epochs.

Required additive migration: Device.recoveryPinHash, Device.recoveryFailures, Device.recoveryBlockedUntil, Device.authEpoch and RefreshToken.authEpoch. Defaults preserve current identities and entitlements. No existing VIP value/expiry/redemption/purchase is rewritten. No new runtime dependency or environment variable. Apply scripts/migrate-device-recovery.sql before the new backend starts; new APIs require this backend before installing the APK.
